## 作品要做什么

一个距离传感器定期给出毫米读数，CH32V307 判断状态，再控制绿/黄/红 LED 和蜂鸣器。当前没有电机；`motion_allowed` 只是为将来的电机驱动预留的**逻辑许可**，不是安全认证的刹车功能。

| 状态 | 条件（暂定） | 输出 |
| --- | --- | --- |
| 正常 | 距离大于 600 mm；从警告恢复需达到 700 mm | 绿灯常亮，蜂鸣器关闭 |
| 接近 | 距离不大于 600 mm；从危险恢复需达到 320 mm | 黄灯常亮，蜂鸣器关闭 |
| 危险 | 距离不大于 250 mm；距离回升到 320 mm 才退出 | 红灯常亮，蜂鸣器间歇响；禁止运动 |
| 故障 | 启动尚无数据、驱动报告无效读数，或距上次有效读数达到 300 ms | 红灯闪烁、蜂鸣器短鸣；禁止运动 |

250/320/600/700 mm 是**软件演示初值，不是实测安全距离**。阈值一进一退形成“回差”：障碍物在边界附近微小抖动时，灯不会反复跳变。故障恢复需要连续 3 次有效读数。危险状态由一个有效近距离读数立即进入；没有人为延迟。传感器能否检测断线、量程外或遮挡，取决于其驱动和实际模块，不能仅凭本软件宣称这些情形已被覆盖。

```sh
./guard_replay sim/example_trace.csv
```

推荐统一入口（在本目录运行）：

```powershell
# 只编译；不运行生成的程序
.\验证软件.ps1 -CompileOnly
# 在系统允许正常执行时，运行完整主机验证
.\验证软件.ps1
# 有其他编译器时显式指定
.\验证软件.ps1 -Compiler 'C:\path\to\gcc.exe'
```

也可用已安装的 Python 3 执行 `python tools/verify.py --compile-only`；去掉 `--compile-only` 才会正常启动测试程序。脚本不修改执行策略、不下载编译器，也不绕过系统拦截。若脚本或生成程序被拦截，保留错误并停在编译检查，交给正常授权的开发环境执行。

`build/verification.json` 中 `COMPILE_ONLY_PASS` 只表示编译通过，`HOST_TESTS_PASS` 才表示该源码指纹下的主机测试通过；`FAIL/BLOCKED` 应原样保留。本机使用此前取得的 TinyCC 0.9.27 Windows 包完成当前版本编译检查。旧版运行记录不能覆盖当前新增代码。桌面演示输出始终是**模拟数据**，不能充当上板测试证据。

重放文件每行是 `time_ms,has_new_sample,valid,distance_mm`，按时间严格升序排列；`#` 开头为注释，支持 UTF-8 BOM。拒绝重复/倒退时间、负数、溢出和额外列。时间范围 0–4294967295 ms，布尔值只能是 0/1，距离 0–65535 mm；文件跨过时钟回绕时应切为新的记录段。程序以第一行时间初始化，仅在每条记录处计算输出，**不补算两行之间的每个循环时刻**。要检查 300 ms 超时边界，请在该时刻加入 `available=0` 的行。真实板卡若能导出时间戳与传感器状态，就能填同样格式再回放。重放结果只证明**这些输入在当前软件下会得到什么输出**，不独立证明记录来自实物。

B 档软件仲裁已写成 `fusion_decide`，但当前 A 档 `app_tick` **不会调用它**。决定升级 B 后，应在同一个板卡主循环里完成“读传感器→`guard_update`→读并消抖碰撞开关→`fusion_decide`→一次性写物理输出”。不能先让 A 档 `app_tick` 写输出、再覆盖成 B 档输出，否则会出现短暂的错误状态。

`contact_update` 在首次读到按下时立即触发；“立即”指本次软件调用，不代表零物理延迟。松开后连续 30 ms 未再次读到按下才释放（模板值，须实测）；启动也先等一次稳定松开。短于轮询周期的接触脉冲可能漏读，若实测出现，应检查采样/中断方案。它不能靠软件识别普通两线开关断线。

C 档 `adaptive_trigger_distance` 对实测停转表采用“取不低于当前速度的下一个校准点”方式，再加实测响应时间内的前进距离和固定余量，并保留最小阈值。表中应填同一负载、供电和地面条件下**多次测试的最大停转距离**，不能填平均值冒充上界。速度超出校准表、表格顺序错误或结果溢出时返回失败；板级程序此时应进入故障/禁止运动，不得继续使用一个无来源的旧阈值。**当前测试里的校准点是人造示例，不代表真实小车。**

1. 取得实际 CH32V307 板卡的原理图、资料包和传感器型号；按它们确认电源、信号电平、GPIO 和蜂鸣器电流。不要照搬其他 PCB 的接线图。
2. 在 MounRiver Studio 官方例程中先跑通下载、LED、毫秒时钟；再单独读出传感器原始值，记录无障碍、近距离、超时/断线的真实表现。
3. 实现 `board_init`、`board_millis`、`board_poll_distance`、`board_write_outputs`、`board_delay_ms`，把 `src/guard.c`、`src/app.c` 和 `board/board_main_template.c` 加入板卡工程。传感器每次**新结果**返回 `available=true`；正常读数返回 `valid=true`、毫米值；明确超时/错误返回 `valid=false`；尚无新结果返回 `available=false`。不能把上一次读数反复伪装为新结果。`board_poll_distance` 必须快速返回，不能在里面长时间等待一次测距结束，否则故障提示和灯光刷新也会被卡住。
4. 每 10 ms 调用一次 `app_tick`，传感器以约 50 ms 周期更新；若实际传感器更慢，按实测周期调整 `sample_timeout_ms`，始终让它明显长于正常采样间隔。LED、蜂鸣器和未来电机负载都要按电路规格驱动，不直接让 GPIO 承担超规格电流。

   应用层在读取输入完成后取当前时间，再判断超时和输出；不能复用总线读取前的旧时间。即使一次读操作只有 1 ms，也可能跨过超时边界。此顺序不取消驱动快速返回、有界等待的要求。
5. 上板后先复现“正常→接近→危险→故障→恢复”，再记录至少 10 次重新上电、约 30 分钟连续运行、误报/漏报和响应时间。失败项原样保留；只有实测通过才能写进参赛材料。

**下一步**：板卡和传感器到手后提供清晰型号、原理图/接线资料与一次原始读数记录，才能把模板变成可烧录工程。**停止条件**：官方 LED 例程或传感器独立读数尚未稳定时，不接入整套业务逻辑；核心闭环尚未稳定时，不加电机、联网或第二传感器。
